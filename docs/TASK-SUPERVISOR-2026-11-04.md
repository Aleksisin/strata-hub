## 0. Зачем (зафиксированные травмы, которые Supervisor исключает)

Каждое требование ниже — конкретный инцидент 03–04.11, не теория:

| Требование Supervisor | Инцидент-прообраз |
|---|---|
| Единственный владелец GPU-слота | ~20 задач StrataHub сработали разом в 23:59 (шторм триггеров) |
| Запрет `taskkill` по имени образа | FIX-чейн убил контрольный бенч и загрузку шлюза `taskkill python.exe`; под ударом был и Hermes |
| Завершение по артефактам, не по exit code | трижды зафиксирован «exit 0» при убитом/пустом прогоне |
| Атомарность результатов | `move` из корня runs\ перетёр архивы перекрёстными записями; results.json восстановлен из bundle.json |
| Flush логов | буфер stdout шлюза потерял хвост ctl-лога при taskkill |
| Состояние задания на диске | после аварийного завершения supervisor не знал, что стало с заданием |
| Изоляция дерева процессов | единственный механизм «убийства» — по образу/окну; Job Objects отсутствуют |

## 1. Объём v1 (обязательно / отложено)

**Обязательно в v1:**
1. Единственный владелец GPU — мьютекс слота; второй владелец отклоняется.
2. Очередь заданий — файловая (см. §3), FIFO, без HTTP API.
3. Уникальный `run_id` и каталог прогона — создаётся ДО старта процесса;
   бенч пишет `--out` прямо в него (этап «move» исчезает).
4. Проверка итоговых артефактов — переход в DONE только после валидации (§5).
5. Перезапуск после сбоя supervisor'а — сверка состояния на диске (§6).
6. Manifest с хэшами конфигурации (§7) — пишется до и после прогона.
7. Job Objects для дочерних процессов (§4) — никакого `taskkill python.exe`.

**Отложено (НЕ делать в v1):** HTTP API и веб-панель; управление моделями и шлюзами
(поэтапно после v1); автоматический выбор модели; CheckRunner (следующий этап, §9);
Loop guard (§10).

## 2. Архитектура

- **Язык:** Python 3.14 (stdlib + pywin32 для Job Objects; pywin32 при отсутствии —
  ctypes-обёртка CreateJobObject/AssignProcessToJobObject/TerminateJobObject).
- **Запуск:** один пункт Task Scheduler (`StrataHub\SUPERVISOR`), триггер — прошедшая
  дата, `/Run` вручную; автостарт при загрузке Windows — настройка за оператором.
- **Каталог:** `C:\Users\shogu\Strata-Hub\supervisor\` — код; состояние —
  `supervisor\state\` (очередь, статусы, lock-файлы); логи — `supervisor\logs\`.
- **Живость:** health-проверка = HTTP не нужен; для оператора — файл
  `state\supervisor.json` (pid, время пульса, текущее задание).

## 3. Файловая очередь заданий

Задание = JSON-файл в `supervisor\queue\pending\<run_id>.json`:

```json
{
  "run_id": "20261104-abrep-r3",
  "kind": "peakstone",
  "cmd": ["C:\\...\\peakstone-bench.exe", "--gateway", "http://127.0.0.1:8109",
           "--models", "nanoplus-v3-agent16k-r3", "--ids-file", "...quick59_ids.txt",
           "--max-tokens", "16384", "--no-judge", "--bundle",
           "--out", "C:\\...\\runs\\<run_id>\\"],
  "workdir": "C:\\Users\\shogu\\Strata-Hub\\peakstone-repo",
  "run_dir": "C:\\Users\\shogu\\Strata-Hub\\peakstone-repo\\runs\\<run_id>",
  "validate": {"kind": "peakstone59", "expected_ids": 59,
               "ids_file": "C:\\...\\quick59_ids.txt", "bundle_signature": true},
  "manifest": {"model_gguf_sha256": "...", "gateway_sha256": "...",
               "engine": "llama.cpp 8107", "profile": "agent-full"}
}
```

Приём: положить файл в `pending\`. Supervisor атомарно (rename) переносит в
`active\`, создаёт `run_dir`, запускает. Статусы — `state\<run_id>.json`.

## 4. Процессы: Job Objects, изоляция дерева

- Каждому заданию — **свой Job Object** (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`),
  дочерний процесс назначается в job при старте. Убийство задания =
  `TerminateJobObject` — гасит ровно его дерево (бенч + его python-детей),
  **не затрагивая** Hermes, Pi, шлюзы и движки (приёмочный тест 5).
- Supervisor сам живёт в отдельном job с kill-on-close — обрыва ZCode-сессии
  не убивает (запуск строго через Task Scheduler, сессия 0).
- stdout/stderr задания — в `supervisor\logs\<run_id>.log`, **флаш после каждой
  строки** (python `-u` либо line-buffered re-open).
- Таймаут задания — поле `timeout_s` в JSON; истечение = TerminateJobObject +
  статус FAILED(timeout) + валидация артефактов всё равно выполняется.

## 5. Автомат состояний задания и валидация

```
QUEUED → RUNNING → VALIDATING → DONE
                     ├→ FAILED_INVALID   (артефакты не прошли валидацию)
                     └→ FAILED_TIMEOUT   (убит по таймауту)
RUNNING → INTERRUPTED                (supervisor перезапустился, процесс мёртв)
RUNNING → DONE (после валидации)     (процесс умер, но артефакты полные)
```

- **DONE только после валидации** — ни при каком exit code.
- Валидатор `peakstone59`: results.json существует; ровно 59 результатов; ID
  совпадают с ids_file 1:1, без дублей; у каждого финальный score (число, может
  быть 0); bundle.json существует и подписан; расхождение = FAILED_INVALID.
- Валидаторы других видов добавляются по мере надобности (`niah-ladder`, `ppl-pair`).
- **Автоповторов НЕТ**: нельзя автоматически перезапускать задание — побочные
  эффекты (движки, шлюзы, файлы) неизвестны. Повтор = новое задание от оператора.

## 6. Восстановление после падения Supervisor

При старте supervisor сверяет каждое `state\<run_id>.json`:
- статус RUNNING → жив ли PID процесса (и его job)? жив → перевести наблюдение
  обратно (re-attach: дождаться завершения и валидировать); мёртв → VALIDATING
  по артефактам → DONE/FAILED_INVALID/INTERRUPTED.
- QUEUED в `pending\` → остаётся в очереди (потери очереди нет — приёмочный тест 3).
- ACTIVE-файл без состояния → восстановить статус из содержимого.

## 7. Manifest (пишется в `run_dir\manifest.json`)

До старта — конфигурационная часть, после валидации — результатная:

```
run_id, created_utc, kind,
model: { name, gguf_sha256 },
engine: { name, port, binary_sha256 },
inference: { context, max_tokens, temperature, seed },
tools: { profile, gateway_sha256, allowlist_sha256 },
benchmark: { suite_sha256, ids_file },
results: { score, n_challenges, transport_errors_ctok0, tool_errors, wall_s,
           status, validated: true }
```

Хэши берутся из фактических файлов на диске (не из документации).

## 8. Приёмочные испытания v1 (все обязательны)

1. **Два одновременных запуска** не занимают GPU параллельно: второй остаётся
   QUEUED до освобождения слота.
2. **Принудительное завершение дочернего процесса** (TerminateJobObject на
   середине прогона) не даёт DONE: статус FAILED_INVALID/INTERRUPTED, артефакты
   сохранены как есть.
3. **Перезапуск Supervisor** не теряет очередь и существующие результаты.
4. **Два прогона не могут перезаписать один results.json**: разные run_dir;
   попытка задания с существующим run_id отклоняется.
5. **Уничтожение одного задания** не завершает Hermes, Pi, шлюзы, движки
   (проверка health 8107/8109/6280 после TerminateJobObject).

**Критерий завершения v1:** последовательность из нескольких бенчмарков проходит
без ручного сопровождения, результаты сохраняются раздельно, аварийная остановка
одного процесса не повреждает остальные, каждое задание получает проверенный
итоговый статус.
