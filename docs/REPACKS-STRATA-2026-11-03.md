## 1. Постановка задачи

Движок strata 0.1.56 (dense-бинарник, GEMV/MMQ-ядра) принимает на входе **ограниченный набор
квантовых типов** (16 шт.): Q4_0, Q5_0, Q8_0, Q2_0(ternary), Q3_K, Q4_K, Q5_K, Q6_K,
IQ1_M, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ4_NL, IQ4_XS; F32/F16/BF16 — неявно.
Кроме того, для гибридных (SSM+attention) архитектур требуются **единообразные по слоям**
тензоры `ssm_alpha`/`ssm_beta` — смесь типов в одном семействе отвергается загрузчиком.

llama.cpp этих ограничений не имеет (переваривает все типы) — поэтому репак делался
**параллельным файлом**, оригиналы не тронуты: llama.cpp-путь (продакшен) продолжает
работать на исходных GGUF, strata-путь получает свою копию.

Дополнительные требования strata (контекст, без которого репак не запускается):
- движок `generate` не читает токенизатор из GGUF — нужен отдельный пак
  (`vocab.json` + `merges.txt` без завершающего \n + `token_type.json`), сгенерированный
  **из самого GGUF** (у семейства Unsloth-производных vocab 248320 ≠ базовых 248044);
- флаг `--native` требует `--ple-gguf` (шард `per_layer_token_embd` strata-формата) —
  для однофайловых GGUF его нет, поэтому путь = дефолтный GEMV/MMQ, без native-ветки.

## 2. Репак 1: Xolotl Qwen3.8-27B UD-IQ3_XXS → «dense2»

| | |
|---|---|
| исходник | `Qwen3.8-27B-UD-IQ3_XXS.gguf` (UD-компиляция IQ3_XXS-микса; из recipes Unsloth) |
| выход | `Qwen3.8-27B-UD-IQ3_XXS-dense2.gguf`, **11 705 768 864 байт (11,71 ГБ)** |
| замена | **21 тензор** → деквант → Q4_0; остальные ~590 копируются байт-в-байт |
| размер | +0,1 ГБ к исходнику (у Q4_0 шире сетка, объём больше) |
| верификация | strata-загрузка `--check`: **ALL PASSED**; повторное чтение gguf-py: тип/форма/статистика норм |

**Что заменено (21 Q4_0-тензор в выходном файле, 1 552,7 МБ суммарно):**
- `token_embd.weight` [5120×248320], 715,2 МБ — был Q2_K (не поддерживается, и это
  эмбеддинг — обязателен к стандартной деквантализации);
- 10× Q2_K и 8× IQ1_S + 3× IQ1_M, разбросанные по блокам: attn_q/attn_qkv/attn_gate,
  ffn_gate/ffn_up/ffn_down (blk.0–blk.49). Полный список имён — в повторной дампе dense2.

**Причина именно этих тензоров:** в исходнике IQ3_XXS-компиляции Unsloth часть тензоров
падала в более дешёвые типы (Q2_K/IQ1_S/IQ1_M). Из них IQ1_M дополнительно **ломает MMQ
префилл-путь** strata (префилл падал с ~1290 до ~132 т/с на промежуточной версии) —
после исключения IQ1_M из SUPPORTED-набора получен замер **prefill ≈ 1290 т/с**.

**Качество (исправлено по ревью 04.11):** замены — это **перекодирование в поддерживаемый
формат, а не апгрейд точности**. Цепочка `W_Q2 → W_FP32 → W_Q4` не восстанавливает исходные
веса BF16/FP16: деквантование возвращает приближённые значения, уже содержащие ошибку
исходного квантования; повторное квантование в более широкую сетку Q4_0 утраченную
информацию не возвращает и может добавить собственную погрешность. Для пар Q2_K→Q4_0 /
IQ1_S→Q4_0 / IQ1_M→Q4_0 точность **не гарантированно растёт** (частный случай: смена
несимметричной сетки Q4_1 на симметричную Q4_0 — возможно ухудшение). Корректная
характеристика обоих репаков: **преобразования совместимости**. Практическая ценность
dense2 подтверждена не точностью, а открытием быстрого MMQ-пути (prefill). Итоговое
качество модели на тестах не переизмерялось (см. §5, пункт 1).

Промежуточные артефакты (оставлены на диске для истории): `-q4emb` (19:43, только
эмбеддинг → Q4_0), `-dense` (19:47, без исключения IQ1_M — тот самый 132 т/с).

## 3. Репак 2: NanoPlus V3 EfficientThink → «strata»

| | |
|---|---|
| исходник | `Qwen3.8-27B-EfficientThink-VAL-APEX-I-NanoPlus-V3.gguf`, 11 176 175 232 байт (11,18 ГБ) — **продакшен-модель стенда** (Hermes-дефолт, llama.cpp 8107) |
| выход | `...-NanoPlus-V3-strata.gguf`, **11 205 379 712 байт (11,20 ГБ, +29 МБ)**, лежит рядом с оригиналом |
| замена | **49 тензоров**: 1× Q4_1→Q4_0 + 48× ssm_beta→F32; остальные копируются байт-в-байт |
| верификация | повторное чтение: `blk.64.ffn_down` Q4_0 50,1 МБ форма [17408,5120], статистика адекватна; ssm-семейство = **uniform F32 ×96** (48 alpha + 48 beta) |

**Дефекты исходника (их ровно два):**
1. `blk.64.ffn_down.weight` [17408×5120] — единственный на весь файл тип Q4_1,
   которого нет в SUPPORTED-наборе strata.
2. Неоднородность ssm-семейства: `ssm_alpha` — все 48 в F32; `ssm_beta` — 47 в Q8_0 +
   1 (blk.0) в Q4_0. Загрузчик strata требует единый тип по семейству слоёв.

**Решение по ssm:** приведение к **uniform F32** (деквант 48 beta-тензоров). По таблице
преобразований: Q8_0→F32 — точное (или близкое к точному) хранение деквантованных
значений, без восстановления исходных весов — т.е. сведение к одному типу без добавления
новой ошибки квантования. Альтернатива «uniform Q8_0» (квантизовать и alpha тоже)
сэкономила бы ~30 МБ, но добавила бы новую ошибку квантования в параметры SSM-рекуррентности
— выбран консервативный F32. Цена вопроса +29 МБ (0,26 % файла). Влияние на качество
рекуррентности — предмет проверки по §6 п.3 (PPL + эталонный набор vs оригинал).

**Токенизатор-пак:** уже собран ранее из этого же GGUF
(`strata_upstream\pack\full\tokenizer`, vocab 248320, merges без завершающего \n,
token_type — плоский список GGUF-типов). Репак копирует KV-метаданные байт-в-байт,
поэтому пак остаётся валидным для нового файла.

**Статус замера скорости:** НЕ ВЫПОЛНЕН — GPU занят контрольным прогоном бенча
(15,8/16 ГиБ). Очередь: strata-load → смок → decode/prefill против llama.cpp-базлайна
(тот же файл, 128K ctx q4_0 KV: decode 54,9 т/с / prefill 147,8 т/с).

## 4. Методология (общая для обоих репаков)

1. Перечень типов: `GGUFReader` → `tensor_type` по всем тензорам (см. таблицы выше).
2. Метаданные копируются через `writer.add_key_value(name, contents, vt, sub_type)` —
   поэлементно, чтобы не потерять ARRAY-subtype у KV-полей.
3. Тензоры в SUPPORTED — `add_tensor(..., raw_dtype=...)` байт-в-байт (деградации ноль).
4. Неподдерживаемые: `dequantize(t.data, type)` → FP32 → `quantize(fp32, target)`.
   Важно: gguf-py возвращает FP32 в транспонированной (out,in)-ориентации — `len()`
   массива показывает первую размерность, НЕ байтовый объём (источник ложной тревоги
   «5120 байт» при отладке — фактический объём тензора в файле 50,1 МБ).
5. Контроль: перечитать выход ридером, сверить тип/форму/размер/статистики каждого
   заменённого тензора.

## 5. Ограничения и что репаки НЕ решают

1. **Качество не переизмерено.** Репаки — перекодирование совместимости (см. §2):
   точность заменённых тензоров не гарантированно растёт, интеграционный эффект
   (все замены сразу) на бенчах не проверен ни для dense2, ни для NanoPlus V3.
   ~~Рекомендуется PPL-фрагмент + эталонный набор (§6 п.3) для обоих выходов.~~
   **Выполнено 04.11: для NanoPlus V3 репака и PPL (§7 П.5: Δ +0.0006), и
   эталонный subset (§7 П.3: +0.28 на variance-качелях) — деградации нет. Для
   dense2 измерений качества по-прежнему нет (модель вне активного контура).**
2. **DFlash2 на strata не возвращается.** В dense-бинарнике DFlash2 отсутствует; есть
   только `--mtp` для модель-зашитой nextn-головы. Основной GGUF NanoPlus V3 головы
   не содержит (отдельно скачанный dflash2-файл — кандидат на проверку `nextn`).
3. **`--native` недоступен**: требует PLE-шарда strata-формата, конвертера нет.
4. **Decode-скорость strata-пути на этих файлах не измерена** (замер prefilla 1290 т/с
   есть только у dense2). Весь смысл репаков — «если скорость вырастет» — пока гипотеза.
5. Исходник `UD-IQ3_XXS.gguf` удалён в чистке диска — восстановим перекачкой (бат
   `dl_ud_iq3xxs.bat`), dense2 самодостаточен для strata, но НЕ читает больше исходник.

## 6. Приоритеты следующих испытаний (порядок по ревью 04.11)

1. **NanoPlus V3 strata — загрузка и генерация.** Повторное чтение GGUFReader'ом — это
   проверка структуры, НЕ inference: репак должен пройти весь путь strata (загрузка
   тензоров в движок, префилл, декод). До этого «NanoPlus V3 strata» — подготовленный
   кандидат, не валидированный исполнитель.
2. **Парное измерение decode/prefill.** Только один GGUF, один промпт, одинаковый
   контекст и одинаковая конфигурация KV в обоих движках. Оптимально —
   `NanoPlus-V3-strata.gguf` в обоих (если llama.cpp корректно его читает — типы
   стандартные, должен). Прежнее сопоставление «dense2 1290 т/с vs NanoPlus V3 147,8 т/с»
   — РАЗНЫЕ модели/артефакты, оценка ×8,7 НЕКОРРЕКТНА и отзывается до парного замера.
3. **PPL + небольшой эталонный набор** (оригинал NanoPlus V3 vs репак): формальная
   проверка последствий Q4_1→Q4_0 (blk.64.ffn_down) и ssm Q8_0/Q4_0→F32.
4. **KV int8/q4_0** — только после базовой проверки движка; отдельный тест точности
   на длинном контексте (KV q4_0 идёт после Hadamard-ротации).
5. **Generic-конвертер — преждевременен**: автоматизировать имеет смысл уже
   подтверждённый рабочий путь (после п.1–3).
6. Справочно, вне приоритета: проверка dflash2-файла NanoPlus V3 на зашитую nextn-голову
   (один grep; открыла бы `--mtp`); вариант B dense2 с целевым типом Q3_K/IQ2_XXS
   (−600…−700 МБ, актуально только при дефиците диска).

## 7. Испытания 04.11 (по приоритетам ревью; «го» оператора)

**П.1 — inference-валидация NanoPlus V3 strata: ПРОЙДЕНА.** `strata-dense.exe --check`:
`check: all passed` (MMQ-префилл 16-чанками vs по-одному: max |dlogit| 0.204 на шкале
12.7 = 1.61%, argmax 286/286; чанки 3,2,5,1,8,4 — bit-identical). Сервер
`serve.server --engine strata --config strata-np3-strata.json --port 8096`
(ctx 131072, KV q4_0) поднялся, генерация идёт (reasoning + финальный ответ, usage
корректный). Репак проходит ВЕСЬ путь — не только чтение ридером.

**П.2 — парный замер (ОДИН файл `...-strata.gguf`, ctx 131072, KV q4_0, fresh cache,
детерминированный промпт 3792–3829 токенов):**

| метрика | strata-dense 8096 | llama.cpp 8107 | разница |
|---|---|---|---|
| prefill | ~1406 т/с (3829 ток / 2.72 c wall; лог: 3.7K/3 c) | **1313 т/с** (лог: 2888 мс / 3792 ток) | strata **+7%** |
| decode | 43.8 т/с (лог: 256 ток / 6 c) | **52.3 т/с** (лог: 1512 мс / 80 ток) | llama.cpp **+19%** |

Вывод: ×8,7 от dense2 НЕ подтверждается на парном замере — реальный выигрыш prefill
~+7%, decode strata проигрывает. Прежнее сравнение было межмодельным артефактом
(д dense2 1290 т/с и llama.cpp-прод 147,8 т/с — разные файлы и разные условия/длина
KV). **Стратегического основания переводить NanoPlus V3 на strata нет**: llama.cpp
остаётся продакшеном (быстрее на декоде, паритет на префилле ±7%).
Методологические ловушки пары: prompt-cache llama.cpp доедает префилл второго
запроса (LCP-reuse — замерять по первому или чистить слот); счётчики prompt_tokens
чуть различаются шаблонами (3792 vs 3829) — скорости считать по своим логам.
**Оговорка по ревью 04.11 (для строгости публикации):** decode мерялся на 256 токенах
у strata и 80 у llama.cpp, повторений нет — точные проценты требуют равных длин
генерации и повторов; `ctx=131072` — настроенная ВМЕСТИМОСТЬ, фактический проверенный
промпт ~3.8K токенов. Для решения об отказе от миграции измерений достаточно,
для строгого сравнения движков — нет.

**П.3 — эталонный subset вместо PPL** (в unsloth-билде нет llama-perplexity;
замещено 9 задачами one-shot-протокола через llama.cpp 8107 на репаке, подписанный
бандл `runs/np3-repack-subset/`): bcb-0008/0010/0011/0012/0013, algo-ds-01,
algo-graph-01, algo-greedy-01, gsm8k-0008. Итог: сумма 6.80 (оригинал) → **7.08

задокументированных variance-качелях, кувыркающихся и на оригинале (bcb-0011: 0
в one-shot → 1.0 в r2; algo-ds-01: 1.0 → 0 в r2 и fixup на оригинальном файле).
Деградации качества от Q4_1→Q4_0 (blk.64.ffn_down) и ssm Q8_0/Q4_0→F32 НЕ
обнаружено. Формальный PPL остаётся опциональным уточнением.

**П.4 — KV int8/k8v4: ОТМЕНЁН оператором (04.11)** — смысл потерян вместе с вопросом
о переводе движка (П.2 показал, что перевода не будет). Справочно: парный замер П.2
