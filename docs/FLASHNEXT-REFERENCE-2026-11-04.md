## 1. Что это

- **Qwen3.8-Flash-Next** — 125B MoE (6B активных) мультимодальная модель Qwen на новой
  архитектуре **Qwen4**: 512 экспертов (10 routed + 1 shared на токен), 48 слоёв,
  гибрид **Gated DeltaNet + Qwen Sparse Attention (QSA)**, Gated Residual, **n-gram
  эмбеддинги (PLE)** 51.2B значений (per_layer_token_embd 160×320,001,536), MTP-голова
  4B. Суммарно в GGUF ~177B параметров.
- Контекст: **262 144 нативно**, YaRN до ~1M (rope_parameters/factor — менять только при
  необходимости длинных контекстов).
- Заявка вендора: outperforms Claude-4.6-Opus (Max). Лицензия qwen-community-1.0.
- **Важно для нас:** это РОДСТВЕННИК нашего NanoPlus V3 (та же гибридная Qwen-архитектура
  с ssm/DeltaNet) и та самая модель из Habr-статьи (60 т/с через strata offload).

## 2. Dynamic V3.1 (обновление 04.11.2026) — что означает «+15%»

Новый алгоритм квантования Unsloth **Dynamic V3.1 (preview)** — «15% more accuracy than
OTHER FRONTIER QUANTS» = против квантов ДРУГИХ провайдеров, НЕ против прошлых весов.
Methodology: **26.2B токенов бенчмарков** (DeepSWE 18.1B + Terminal Bench 5.2B), temp 1.0 /
top_p 0.95 / top_k 20 / min_p 0, без presence/repetition, preserve_thinking, xhigh;
агентные бенчи на 256K (не YaRN), обычные на 128K; многократные прогоны (LCB ×3, HMMT ×8-16).
PLE/Ngram НЕ квантуются агрессивно — минимум 4-bit (IQ4_NL), т.к. random access pattern,
жёсткое квантование ломает модель.

## 4. Требования к памяти (RAM+VRAM суммарно) и наш стенд

| 1-bit | 2-bit | 3-bit | 4-bit | 5-bit | 8-bit | BF16 |
|---|---|---|---|---|---|---|
| 75 GB | 79 GB | 90 GB | **96–114 GB** | 163 GB | 200 GB | 355 GB |

С MTP: +1-2GB (3-bit+MTP 91, 4-bit+MTP **97–115**).
**Наш стенд: 128 ГБ RAM + 16 ГБ VRAM = 144 ГБ → 4-bit ВЛЕЗАЕТ (96–114, с MTP 115), 5-bit (163) — НЕТ.**
Заявка Unsloth: CPU/RAM-инференс этой архитектуры почти не уступает VRAM; PLE/Ngram можно
выгружать на SSD через mmap. Минимальный квант живёт на 75 ГБ RAM (без GPU).
Развёртка: эксперты/engram в RAM (llama.cpp MoE offload), attention/KV в VRAM.

## 6. Engram (PLE/n-gram таблицы) — механика шардирования

- Таблица 51.2B значений лежит **ПОСЛЕДНИМ шардом кванта**: у UD-Q3_K_XL и UD-Q4_K_XL
  слот `-00004-of-00004`, в бандле **IQ4_NL 28.8 GB** (RMSE 0.0757 vs BF16).
- Размеры шаров UD-Q3_K_XL: 0.01 + 49.74 + 10.91 + 28.8 = 89.47 GB (в доке 90.0).
- Размеры шаров UD-Q4_K_XL: 0.01 + 49.72 + 32.8 + 28.8 = 111.33 GB.
- **Шард 4 у Q3 и Q4 — БАЙТ-В-БАЙТ ОДИН ФАЙЛ** (LFS sha256
  `5de8b5dbf89409acc39468decafd4a4a95b13c29d88a14b0356107897829ec36`) → скачав Q3-сет,
  Q4 добирается тремя шарами, энграма копируется.
- Апгрейд таблицы (если захотим точнее): Q8_0 54.4 GB (RMSE 0.0053) / Q5_1 38.4 (0.0376) /
  BF16 102.4 (0) из папки `engram/` (файлы `.gguf_file` — сканеры моделей их не видят).
  Процедура: `set_split.py <file> <slot> <count>` (пишет split.no=slot-1, split.count,
  0-based внутри) → переименовать в имя табличного шарда своего кванта. Сурс set_split.py
  — в доке и в репо (plain Python).
- K-квантам (Q5_K/Q6_K) такая таблица противопоказана (строки 160 не кратны 256).

## 7. MTP (Multi-Token Prediction)

- **×1.3–1.7 скорости без потери точности**; на RTX 6000 PRO: 170 т/с против 100 базово.
  На низкополосных устройствах (старые Mac) выигрыш меньше.
- Файлы: общие (General) и **shared** (без embed_tokens, экономия 1-2 GB):
  BF16 7.77/5.23 · Q8_0 4.14/2.79 · Q4_K_M 2.79/**1.91** GB.
- Требования с MTP: 1-bit 76 / 2-bit 80 / 3-bit 91 / 4-bit **97–115** / 5-bit 164.
- **llama.cpp: нужен КАСТОМНЫЙ бранч** `danielhanchen/llama.cpp#qwen4exp/mtp`
  (mainline без этого MTP!). Запуск:
  ```
  llama-server -hf unsloth/Qwen3.8-Flash-Next-GGUF:UD-Q4_K_XL \
      -md .../MTP/mtp-Qwen3.8-Flash-Next-shared-Q8_0.gguf \
      --spec-type draft-mtp --spec-draft-n-max 5
  ```
  Число draft-токенов настраивается (Unsloth Desktop advanced; у нас — флагом).
- **Открытый вопрос для стенда:** наш b11985-mix уже умеет `--spec-type draft-mtp` для
  qwen-семейства (проверено на NanoPlus/GSX) — поддерживает ли он MTP-голову Qwen4/
  qwen4exp-архитектуры ЭТОЙ модели — проверить смоком; если нет — собирать
  qwen4exp/mtp-бранч в ОТДЕЛЬНЫЙ каталог (не трогать живые DLL).

требованию) vs `--lazy-mode off` (резидентно, если RAM позволяет). Метрики не
только tok/s: RSS процесса, VRAM, hard page faults, дисковые чтения. При
интенсивном paging второй вариант прекращать. Считать TTFT.

## 10. План испытаний (ревизия 2 по ревью оператора: GO, четыре тех. момента)

**Серия A — AR-база (без MTP, без mmproj, короткий контекст):**
1. Свежий mainline-бинарник собран и подтверждён (LLM_ARCH_QWEN4EXP в исходниках,
   --help-флаги на месте — build-flashnext.log, ALL DONE 04.11 21:53).
   **Сборка ≠ совместимость модели**: критерий = загрузка ВСЕХ 4 шардов, корректная
   инициализация PLE, успешный prefill/decode. В логе загрузки проверять:
   распределение тензоров CPU/GPU, фактический объём выделенной памяти, отсутствие
   unsupported ops.
2. Smoke Q3_K_XL: порт 8111, `-c 8192 -np 1 -ngl auto --cpu-moe --flash-attn on
   --lazy-mode auto` → анти-мускул (связный типизированный текст). НЕ запускать
   262K сразу: 8K → 32K → расширять.
3. **PLE-резидентность — главный риск (уточнено ревью):** 111.3 ГБ Q4 на 128 ГБ RAM
   оставляют мало запаса под ОС/буферы/процессы; RAM+VRAM не единый пул. A/B:
   `--lazy-mode auto` (чтение PLE с диска по требованию) vs `--lazy-mode off`
   (резидентно). **Метрики Windows — не только RSS**: Private Bytes, Working Set,
   Commit Size, Hard Faults/sec + дисковые чтения. Высокий SSD-трафик при paging
   может сделать даже качественную модель непригодной для агентных задач —
   вариант с paging прекращать.
4. Скорость: decode/prefill/TTFT, против NanoPlus V3 ~50 т/с.
5. RU-пробы + refusal-пробы (Groot-урок).

**Серия B — Q3 vs Q4** (без MTP, одинаковый протокол, одна сборка, один порт).
**Серия C — MTP отдельно** (сборка qwen4exp/mtp-бранча): без MTP (эталон) /

**КРИТЕРИЙ ОСТАНОВКИ перед длительным AgentBench (ревью п.4):** после smoke —
КОРОТКИЙ тест производительности с РЕАЛЬНЫМИ размерами промптов и ответов (не

качеству, только неподходящая аппаратная конфигурация). Приоритетная метрика —
**время до корректно завершённой задачи**, не пиковые tok/s.

**Критерии «стоит ли Flash-Next ресурсов» (не NanoBench/Quick одни):**

| критерий | что мерять |
|---|---|
| Качество | IBF-AgentBench, ОДНИ И ТЕ ЖЕ 10 задач |
| Скорость | prefill, decode, TTFT |
| Работа агента | first-try %, число исправлений (fix_cycles) |
| Вычислительная цена | успешные задачи на GPU-час |
| Устойчивость | 32K/128K/262K, потеря информации (NIAH-лестница) |
| Инструменты | корректность вызовов и аргументов MCP |
| Ресурсы | Private/Working Set/Commit, VRAM, диск, Hard Faults/sec |

**Два сравнения обязательно:** (а) каждая модель на своих РЕКОМЕНДОВАННЫХ
настройках (Flash-Next: temp 1.0/top_p 0.95/top_k 20, effort по серии; NanoPlus:
его APEX-сэмплинг) и (б) на ФИКСИРОВАННОМ протоколе, где допустимо — иначе
изменение sampling/reasoning_effort можно принять за преимущество архитектуры.

**Порядок (финал ревью):** завершение конвейера baseline → проверка сборки →
Q3 smoke → резидентность PLE → Q3/Q4 → MTP → AgentBench.

**Суждение о замене NanoPlus** — преждевременно; Flash-Next может получить
ОТДЕЛЬНУЮ РОЛЬ для сложных задач, даже если заметно медленнее основного агента.
Самая ценная гипотеза — сохраняет ли архитектура с 6B активных преимущества
крупной MoE при размещении большинства весов в системной памяти.

## 12. РЕЗУЛЬТАТЫ СЕРИИ A (05.11, ночь) — ВЕРДИКТ ПО КРИТЕРИЮ ОСТАНОВКИ

**Совместимость qwen4exp ПОДТВЕРЖДЕНА** (главная техническая победа): свежий
mainline c6a0ff11a0fe грузит все 4 шарда Dynamic v3.1, PLE инициализируется,
генерация связная (анти-мускул PASS, finish=stop). Наш b11985-mix не знает арх —
сборка была обязательна и сработала.

**Матрица размещения (UD-Q3_K_XL, 8K контекст, тёплые замеры):**

| конфиг | prefill т/с | decode т/с | память |
|---|---|---|---|
| A: `--cpu-moe --lazy-mode auto` | 12.9 | 16.1 | WS 29 ГБ (mmap), VRAM 7.0 ГБ |
| **B: `--cpu-moe --lazy-mode off`** | **23.1** | **16.3** | WS 30.6 ГБ, VRAM 7 ГБ |
| C: cpu-moe + n-cpu-moe 36 (конфликт флагов) | 21.7 | 16.0 | == cpu-moe |
| D: n-cpu-moe 36 без -ot | CRASH | — | PLE 28.8 ГБ → VRAM OOM (нужен -ot) |
| E: `-ot .per_layer_token_embd.=CPU --n-cpu-moe 36` | 9.8 | **5.7** | VRAM 15.4 ГБ забита; PCIe-сериализация хуже всех |

**ВЕРДИКТ: критерий остановки СРАБОТАЛ — полный AgentBench A/B НЕ ЗАПУСКАЕТСЯ.**
Декод 16.3 т/с = точный потолок DDR4: 6B активных × ~3.5 bpw ≈ 2.6 ГБ/токен,
эффективная полоса ~42 ГБ/с → 16 т/с. Любая раскладка (B/E) это не меняет;
лучший префилл 23 т/с против 1300 у NanoPlus. Агентная задача, стоящая NanoPlus
5–50 мин, здесь стоит часы: префилл 30K промпта = ~21 мин на РАУНД. Против
NanoPlus (50 декод / 1300 префилл): декод ×3, префилл ×55 медленнее.

Заявления Unsloth «near-VRAM performance on RAM» подтверждаются только на
широкополосной unified-памяти (Apple/DGX Spark ~300-800 ГБ/с); на DDR4-3200
dual-channel (~42 ГБ/с) архитектура 6B-активных не спасает. MTP (×1.3–1.7 =
21–27 т/с декод) вердикт не меняет; Q4 ~25% медленнее Q3.
