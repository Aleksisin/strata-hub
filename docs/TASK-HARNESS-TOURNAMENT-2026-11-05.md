# ЗАДАНИЕ: Турнир harness — независимые агентные реализации на одной модели

Дата: 05.11.2026. Постановка: оператор (GO на независимый турнир harness после
диагноза файловой наблюдаемости в AgentBench runner'е). Приоритет: **штатный Pi →
DeepSeek Harness → mini-SWE-agent** (исследовательский контроль; OpenHands/OpenCode —
следующие кандидаты, для Windows-стенда дают инфраструктурные затраты).

## 0. Мотивация (зафиксирована ревью 05.11)

1. **0/5 багфиксов первой серии нельзя приписать ни NanoPlus, ни штатному Pi.**
   AgentBench runner — СОБСТВЕННЫЙ агентный цикл (read_file с дефектом 12 КБ —
   найдено и исправлено); Pi как полноценный coding agent имеет свои инструменты
   (read с offset/limit, edit, bash, grep), цикл и работу с контекстом.
2. Внешние данные (Terminal-Bench 2.1, одна модель DeepSeek V4 Flash, 89 задач):
   Codex 73 (82.0%) | Pi 66 (74.2%) | DeepSeek Harness 65 (73.0%) | OpenCode 58
   (65.2%). Данный ряд НЕ устанавливает причинного превосходства (DSH тестировался
   позднее); второе исследование (66 конфигураций): эффективность зависит от
   сочетания модель × harness × тип задач.
3. Архитектурный вывод оператора: **не создавать ещё один универсальный агент, а
   объективно выбирать лучший harness для локальной модели и конкретной работы.**
   Strata Supervisor остаётся оркестратором, IBF-AgentBench — системой оценки,
   исполнитель становится ЗАМЕНЯЕМЫМ КОМПОНЕНТОМ.

- Репо: github.com/deepseek-ai/deepseek-harness (master, MIT, Cordis «everything is

- **Провайдер (напрямую 8107):** `~/.dsh/profiles/headless/cordis.patch.yml`:

### 2026-11-05 — Post-mortem запусков MTP-свипа (4 инцидента, 3 корневые причины)

1. **Действия задач указывали на несуществующие файлы.** Задачи
   NP3-MTP2/MTP3/MTPTEST были созданы с путями без префиксов START-/CHAIN-
   (файлы называются START-NP3-MTP2.bat и т.д.). schtasks /Run печатает
   «УСПЕХ» (просто ставит в очередь), инстанс стартует и мгновенно умирает
   (cmd не находит файл) → LastTaskResult 0x1, лог не создаётся вовсе.
   Журнал TaskScheduler Operational на стенде ОТКЛЮЧЁН — LastTaskResult был
   единственным сигналом. Фикс: schtasks /Change /TR на реальные пути.
2. **cmd-цепь v2: goto после `call` другого bat пропускал фазы.** Цепь v2
   прошла фазы MTP2/MTP3 за ~20 с каждая (2 итерации ping) без «MTP2 up» и
   без «FAILED» — циклы goto молча выпадали после call. Эмпирическое
   правило: cmd-цепи с call+goto ненадёжны; последовательную логику с
   health-ожиданием вести в python.
3. **`start "" /b cmd /c` из python-контекста с piped stdio молча не
   запускает сервер.** Бат стартера сработал (эхо в логе), но llama-server
   не стартовал: редирект `>` сервера даже не обрезал лог. Финальное
   решение v4: llama-server запускается ПРЯМЫМ python Popen с точным
   списком аргументов прода (ноль cmd-кавычепасти).
4. Сопутствующее: лог цепи v1 был смешанной кодировки (ANSI + UTF-16 от
   PowerShell-appends) — Read-инструмент его отказывался читать; в v4 лог
   пишет только python, UTF-8.

### 2026-11-05 (поздний вечер) — РЕВЬЮ обновлённого документа: вердикт подтверждён, три уточнения внесены

**Подтверждено ревью:** откат MTP3 при 131K обоснован; abx5-перезапуск — правильное решение; причина неудачи abx4 — резкая деградация производительности (8.9× по наблюдаемой скорости), НЕ снижение качества NanoPlus.

**Уточнение 1 — WDDM-spill не подтверждён окончательно.** Совокупность фактов (fit-warning при буте, 3.8 т/с, таймауты, чистый бут без MTP) убедительно указывает на проблему размещения памяти, но конкретный механизм (spill в shared GPU memory) требует ПРЯМОГО замера (shared GPU memory / метрики размещения под нагрузкой). До такого замера формулировать «WDDM-spill подтверждён» нельзя — только «VRAM placement degradation, механизм вероятен».

**Уточнение 2 — MTP не делает бенчмарк автоматически невалидным.** Расхождение текстов при одинаковом seed означает лишь, что побайтовое сравнение не может быть ЕДИНСТВЕННЫМ тестом корректности; сравнение MTP vs обычного декодирования допустимо с независимыми верификаторами и повторными прогонами. abx4 непригоден для сравнения качества агентного контура прежде всего из-за ресурсной деградации и четырёх infra-отказов, а не из-за недетерминизма MTP как такового.

**Уточнение 3 — устаревшие записи помечены.** Исторические формулировки о принятом MTP3 и очереди abx4 сохранены, но явно помечены [SUPERSEDED] (секция MTP-свитча, строки таблицы раундов, смок-строка) — чтобы автоматические анализаторы не выбрали неверную production-конфигурацию.

### 2026-11-05 ночь — предраундная отладка запуска dsh под Windows (4 класса ошибок, все отличны от ошибок модели)

Классификация ошибок ЗАПУСКА (по требованию ревью — отдельно от ошибок модели):
1. **NO_ADAPTER** («no adapter registered for provider "strata-local"»): провайдеры
   pi-ai-адаптера читаются из компонента **`llm-pi-ai`** (NS-константа), а не из
   `llm` (ядро-реестр только валидирует). Патч направлен в правильный компонент.
2. **«No API key for provider»**: pi-ai берёт ключ из ENV по имени (`apiKeyEnv`),
   инлайн-ключ не читает → `apiKeyEnv: STRATA_LOCAL_API_KEY` + переменная в env
   драйвера (llama.cpp ключ не проверяет).
3. **cmd-квотинг многострочных statements через npm-шим**: argv → cmd.exe →
   «Не удается найти указанный файл» на разорванном фрагменте. Решение: промпт
   через **stdin** (dsh читает `-`, pi -p читает stdin без позиционного промпта).
4. **WinError 2 на bare-именах** (`pi`): Python-subprocess не резолвит npm-шимы —
   только полные пути к .cmd (pi.cmd, dsh.cmd).

Инфраструктура драйвера: `agentbench\tournament_run.py` — реюз prepare_copy +
verify_* раннера (один верификатор для всех), worktree на base-коммите, оверлей
до старта, wall-кап 3000 с, классы ошибок none/verifier_red/wall_timeout/
harness_launch. Связность dsh→8107 подтверждена полным циклом (thinking→text→
completed); pi→8107 подтверждена JSON-стримом с системным промптом и тулкитом.
Смоки d3 у обоих — до основных 5 задач.

## 5. Стоп-лист и риски турнира

- **Вложенная агентная логика запрещена**: сторонние harness — только напрямую к
  8107; 8109/AgentGW не участвует.
- **Верификатор один для всех** (тест-оверлей + целый файл зелёный) — независимость
  оценки от исполнителя.
- **Модель/промпты/стратегии не менять** во время турнира (иначе смешение эффектов
  модель×harness×стратегия).
- dsh — developer preview («compatibility-breaking changes expected»), Windows
  не тестировался апстримом → результаты фиксировать с версией 0.2.1-rc.5.
- API-ключи локальных эндпойнтов — плейсхолдеры (llama.cpp не проверяет), в репо
  не хранить.
- Про дешёвые победы: сравнивать wall честно — у harness разные накладные расходы
  на цикл; главный критерий из ревью — **сколько задач доведено до проверенного
  результата**, не число вызовов инструментов.
- **Инструкции окружения (ревью 05.11, п.3):** фиксировать, какие проектные
  инструкции прочитал каждый исполнитель (Pi: AGENTS.md/CLAUDE.md discovery —
  какие файлы в worktree; dsh: workspace context). Иначе часть преимущества
  может определяться проектными инструкциями, а не агентным циклом. Для серии
  с AGENTS.md и серии с `-nc` — отдельные строки результатов.
- **Терминология метрик (ревью 05.11, п.2):** показатель в отчётах —
  `first_verification_pass` (верификатор зелёный с первого запуска ПОСЛЕ серии
  правок), не «решено с первой попытки генерации». В runner-отчёте поле
  переименовано (first_try оставлен как alias для совместимости).
- **Заморозка MTP (ревью 05.11, п.1):** для abx4-* выбирается ОДНА конфигурация
  движка (MTP on/off + draft depth), фиксируется в manifest: enabled, depth,
  acceptance по свипу, SHA256 бинарника. Не смешивать MTP-режимы внутри серии.
